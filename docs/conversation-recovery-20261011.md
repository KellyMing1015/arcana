# 追问断线后的状态核对与恢复

日期：2026-10-11

## 问题与证据

用户使用 OpenRouter 的 Gemini 3，追问提示“连接中断，还没有收到完整回应”，手动重试后成功。这句话对应浏览器 `fetch` 或读流的 `TypeError`；模型通过文字流明确返回的错误走另一条路径。

用户提供的 VPS 阶段日志只有成功记录：约一秒多出现首字，随后 `completed`，没有对应失败请求的 `upstream_error`、`not_committed` 或 `replayed`。这些日志不能证明失败具体发生在浏览器、Cloudflare、VPS 代理或模型连接的哪一层。本地另一供应商的三次短连通性请求均成功，也不代表用户的 OpenRouter 线路已实测通过。

代码中可复现的缺口：浏览器连接断开后直接显示失败，没有马上查询服务器是否已经保存回答；模型发送 `stop` 后后端仍等待连接结束，尾部异常可能把已完成的内容判为失败。

## 本次行为

- 查询对话状态增加 `lastCompletedRequestId`。仍校验账号或游客 Cookie，只返回请求编号及已有可见消息，不返回请求指纹、模型配置或隐藏提示词。
- 只有真实 `fetch` 或读流网络错误进入恢复，界面处理中的普通异常与模型明确报错不触发自动重发。
- 完成恢复必须同时核对牌局、请求编号、轮数、原用户文字、原图片和完整回答，避免把另一个标签页的请求当成本次结果。
- 当前请求已经完成：在原回复位置恢复完整答案，只计一次追问，不重新调用模型。
- 服务器仍忙：有限查询，最多 20 秒、8 次，用户暂停可立即终止等待。
- 明确未完成且没有收到正文：原请求编号及完全相同的请求参数自动重连一次。等待期间修改供应商或资料不会改变这次重连的参数。
- 已有正文但未完成、查询失败或缺字段、身份或牌局变化、另一请求完成：不盲目重发，保留现有失败处理和手动重试。
- 明确 `finish_reason: stop` 时先输出该事件正文，再结束上游读取。长度截断、过滤、工具调用、畸形数据及缺少完成标志仍按失败处理。
- 同步更新浏览器资源版本为 `20261011-reconnect`，避免旧脚本与新状态接口混用。

## 真实浏览器验证

使用独立临时数据库、虚构提问、假模型和真实网页路由。测试中主动让本地 HTTP 连接异常关闭，让浏览器真实产生网络 `TypeError`；未向生产账号写入测试聊天，也未调用真实模型。

1. 首字前断线：第一次请求没有完成，状态查询确认后自动发送原请求一次，最终保留一组问答，完成一轮。
2. 服务器已保存答案但完成通知丢失：查询取回完整回答，没有第二次发送，轮数只增加一次。
3. 已收到正文的中途断线：查询确认未完成后不自动发送，轮数不增加；手动重试替换失败消息并正常完成一轮。

前两项结束时合计 3 次追问 POST、2 次状态 GET、2 个完成轮次；包含最初解读共 4 次假模型调用，证明完成通知丢失时没有重复调用。

## 上线与继续排查

不新增运行依赖或数据库迁移。需要同时更新前后端并重启现有服务。保留远程新增的对话提示词，未调整模型、账号配置或便签规则。

修复能处理已完成或首字前未完成的断线恢复，不能消除网络本身的断开。仍需部署后使用用户原来的 OpenRouter Gemini 3 实测；若继续失败，按发生时刻核对日志。`completed` 后重试为 `replayed` 表示答案曾已保存；`not_committed` 且无上游错误更指向下游断开；`upstream_error` 需要继续看固定错误类型和耗时。
