# Arcana 便签结构升级

本文件记录实施约定。它以用户提供的方案为基础，补充计划期限、用户纠正事实、来源核对和删除保护规则；不修改下载目录中的原始文档。

## 便签保存和返回字段

| 字段 | 用途 |
| --- | --- |
| `id`、`topic` | 原条目的字符串编号与 2–4 字主题；模型更新已有条目必须原样保留字符串编号，新条目不指定编号 |
| `headline` | 一至两句核心摘要 |
| `details` | 最多 5 条非空字符串，补充独立事实；允许空数组，不重复摘要 |
| `text` | 程序从摘要和详情生成的兼容正文，编辑后也同步生成 |
| `importance` | 内部重要性，整数 1–3；按对理解用户的帮助程度判断 |
| `last_evidence_at` | 最后一次原话印证的上海日期，`YYYY-MM-DD`；没有可核对日期时为空 |
| `user_edited`、`edited_at` | 用户是否手改及最后手改时间 |
| `edited_text` | 用户最后一次编辑后的独立原文，用于保护纠正事实；不会随着模型改写而更新 |
| `structure_version` | 旧格式为 0，结构整理后为当前版本，避免每轮反复进行首次迁移 |

提炼输出使用 `changed:false` 或 `changed:true` 加完整 `notes` 集合。模型只输出 `id`（已有条目）、`topic`、`headline`、`details`、`importance`、`last_evidence_at` 和可选 `evidence`；不输出程序管理字段。

`evidence` 是 1–4 段逐字用户原话，用于本轮来源核对，核对后丢弃。新增条目必须提供原话。程序从实际匹配发言的 `spoken_at` 计算日期，不相信模型单独提供的日期；没有新依据时保留原日期。再次明确确认相同事实也算有变化，可只更新确认日期，不改措辞。原话引用真实并不证明摘要中的每个推论都成立；语义规则仍要求事实确有支持。

每条摘要和详情拼接的总正文最多 300 字；最多 20 条，总正文最多 6000 字。本次将原本的 3000 字整组上限提高至 6000 字。超过任一上限拒绝整批结果、保留原便签；不能通过截掉句尾或悄悄丢掉条目来满足限制。

旧数据启动时保留原文和身份，原 `text` 复制为摘要，详情留空，重要性默认 2，未知原话日期留空，标为尚未整理。不会在启动时调用模型或直接删改旧正文；下次正常提炼再做首次整理。

## 提炼规则

每轮审视所有便签；已合格、无新进展的条目保持原措辞。新事实更新同一件事的状态，重复事实合并，不逐句追加。旧格式首次重整可以在没有新事实时进行，删除重复、发言日期流水账、自评和抽象感受，不补入无依据的新事实。

只记录持续的具体处境、与处境相关的事实、决定、约束，以及用户明确表达的沟通偏好。不保存人格评价、情绪自评、哲学感悟、当时情绪、塔罗解读和预测。问题、愿望和假设不等于发生过的事实。

禁止的是“某日你说……”的记述方式。真实计划截止日、实际发生日期和必要时间约束仍保留。期限过去只能说明旧计划的进展需要确认，不能推定完成、失败或放弃。

重要性不按篇幅、情绪强度或重复次数计算。核心处境和重大约束为 3，有用相关背景为 2，次要背景为 1；未受新信息影响时不随意改变权重。

## 用户编辑和删除保护

用户允许自动重新提炼手改条目的措辞，同时保留她纠正过的具体事实。保存独立的最后编辑原文 `edited_text`；模型后来追加的文字不加入该原文。只有 `edited_at` 之后用户明确提供的新进展才能更新纠正事实，旧会话不能改回去。手改条目必须保留编号，完整集合不能遗漏它；新条目和换主题也不能重述与用户纠正矛盾的旧事实。

清理例外仅限全文没有任何值得保留的具体事实或明确沟通偏好、只有自评和抽象感受的旧手改条目。提炼完整集合可以遗漏这种条目以请求清理；程序构造 `key=remove:原id`、`proposed_note=null` 的单独候选，经语义复核批准才删除。混合条目应重提炼其中的具体事实，不能批准整条遗漏；陈旧、结束和篇幅长都不是删除纠正事实的理由。

用户删除的事实不能通过同义改写恢复，只有删除之后用户明确重提才允许再记。编辑前的整段旧文可能在删除记录中，当前编辑原文仍保留的事实不因此被误删。新的否定和事实变化不等于恢复被删掉的旧事实。

对于无新证据的正文重写、需要判断删除事实是否恢复的候选，以及存在任一手改便签时的新增或正文改写，额外调用 `prompts/profile_review.md` 做语义校对。校对输入包含所有手改便签的纠正依据 `corrections`，判断跨条目的相关事实是否被旧话推翻。它只返回获准的候选 key，不生成新便签；无法确认时保留原内容并进入有限重试。未改变条目不重复审核。这会在必要时增加少量模型调用，不是持久的证据存储系统。结构校验规范存取，原话核对验证引用来源，实际筛选、摘要和事实含义判断仍受模型质量影响。

后台整理结果保存前仍检查是否发生新的编辑、删除或开关变化；用户操作优先，防止模型用较早快照覆盖。

## 读取和界面

卡片默认显示摘要，详情浮窗展示补充事实并允许逐条编辑。主题、摘要及详情保存后同步兼容正文。保留“你编辑过”和删除操作；显示“最近提及于”而不是“最后活跃于”。重要性、原话引用和内部近期确认标记不展示给用户。

向解读模型注入便签时，按重要性降序、近期确认优先排序。重要性 2 或 3 且最近 30 天内有确认的便签展开摘要和详情；重要性 1、超过 30 天或日期未知的便签只展示摘要。旧日期标“较久未提及，现状待确认”，未知日期标“尚无近期确认”。这些标记只表示近期缺少确认，不能据此判断事实失效或事情结束。

保存上限是 6000 字，解读注入的便签背景仍沿用 3000 字预算。按排序优先加入；某条详情装不下时只放摘要，摘要也装不下时跳过该条，不修改数据库中的完整内容。

一项新确认不证明同条所有细节仍然有效。旧计划保留具体期限；回答需要依赖尚未确认的阶段性现状时应询问用户。历史牌阵快照、便签提炼触发频率、会话表和专用模型配置维持原流程。

## 本地合成样本评估（2026-10-10）

本地专用便签模型尚未配置，评估在临时 SQLite 中使用虚构对话与便签，通过实际提炼及校对链路调用已有主解读模型；未改动真实数据库和模型配置。业务层共 9 次真实提炼/校对调用，包含一次上游流缺少完成标志的失败及其有限重试。失败时用户手改原文完整保留。测试中根据结果收紧了泛泛催促、旧新状态对比、摘要与详情重复的规则；随后重跑旧流水账和手改样本。

| 样本 | 结果 |
| --- | --- |
| 最终规则下旧流水账首次提炼 | 123 字变为 71 字，摘要加两条详情；去掉“要求高”“找不到依赖的人”、发言日期和笼统催促，保留10月15日期限及未离职状态 |
| 最终规则下手改事实重提炼 | 97 字变为 84 字，并增加等待回复的新进展；保留原编号、手改标记、AI产品运营而非产品经理的纠正、未离职和作品集已完成，语义校对批准 |
| 先前轮次的重复明确确认 | 没有追加一次发言记录，程序将原话印证日期从10月6日更新为10月7日 |
| 先前轮次的新进展 | “未投简历、作品集未整理好”被“已投第一份简历、作品集已整理好”替换，确认日期更新为10月8日 |

仍有轻微冗余：最终手改样本的摘要已经说明转向 AI 产品运营，详情在说明“非产品经理”的排除条件时又复述了一次目标岗位。此次实测证明这些样本中的筛选、状态更新和纠正事实保留有改善，不能保证所有对话都没有冗余，也不能代替上线后专用便签模型的实际表现检查。完整结果、收紧前的输出和失败记录保存在本次临时评估报告中。
